# Track 09: ISO/IEC 27001, from bones to an ISMS

ISO 27001 certifies a *management system* (Clauses 4–10). Annex A is a menu of controls. This repo
implements some Annex A controls technically and generates evidence for them. It cannot implement an
ISMS: management commitment, internal audit and management review are people. This track teaches the gap
honestly, and gives a reader the templates and the map to close it at a real firm.

**Copyright:** use clause and control **numbers and titles only**. Paraphrase requirements in your own words.

**Order:** F03 → F04. Both depend on T15 (risk register and Statement of Applicability).

---

## F03 · ISO 27001: from bones to an ISMS (teaching guide)

- **Wave / mode:** 5 · offline
- **Depends on:** T15; T32 helps (governance templates exist to link)

**Files:** `docs/isms/index.md` and `docs/isms/clause-04.md` … `clause-10.md`, added to the MkDocs nav.

**Each clause page has the same five sections:**
1. **What the clause asks for**, in plain English and your own words.
2. **What this architecture already gives you**, with links. For example:
   - 6.1.2 risk assessment → T15's register;
   - 7.5 documented information → Git history and GitOps;
   - 8.1 operational planning and control → change control through PRs and Argo CD;
   - 9.1 monitoring and measurement → measured drill metrics and the T32 management report;
   - 9.2 internal audit → *not provided*;
   - 9.3 management review → the T32 report is an *input*;
   - 10.2 corrective action → post-incident review and the CHANGELOG "caught live" pattern.
3. **What only people can supply**: the evidence an auditor will ask for that a repo can't produce.
4. **What an auditor would sample from this repo** in a Stage 2 audit, and what they'd find lacking.
5. **Cross-walk** to DORA articles and NIST 800-53 families (link the sheets).

**`index.md` also covers:**
- the certification path: scoping, gap analysis, Stage 1 (documentation review), Stage 2 (implementation), the
  three-year cycle with surveillance audits, and the choice of an accredited certification body (explain
  accreditation, e.g. INAB in Ireland; verify);
- an "ISMS year one" calendar: month by month, which clause activities happen and which artifacts in this repo feed them;
- a RACI using the three-operator model (platform lead, security/compliance lead, on-call responder) plus top management;
- how the SoA (T15) relates to the risk treatment plan, which teams often get wrong;
- the Annex A themes (organisational, people, physical, technological) with counts from the SoA CSV, generated.

**Done when:** eight pages are in the nav, every "already gives you" link resolves, and the strict build passes.

## F04 · ISMS policy templates linked to the controls that enforce them

- **Wave / mode:** 5 · offline
- **Depends on:** F03; T02c (the secrets-model page), T32 (to avoid duplicating the DORA governance templates; link them)

**Files:** `docs/isms/templates/`. Each template is one Markdown file:

| Template | Links to the implementing pieces |
|---|---|
| Information security policy (top-level) | all of the below |
| Access control | Keycloak groups and RBAC, MFA (T14), break-glass exception |
| Cryptography and key management | `docs/guide/secrets-model.md`, cert-manager PKI (T02a) |
| Backup and recovery | Velero schedules, drills, BIA targets (T15) |
| Incident management | runbooks, classification, clocks, GLPI, report drafts (T29) |
| Supplier security | Register of Information (T30), contract checklist (T31) |
| Change management | GitOps, branch protection (D8), CI tests |
| Logging and monitoring | Alloy/Loki, alert rules, retention |
| Vulnerability and patch management | Trivy + KEV SLA, weekly image rebuilds, baselines (F10) |
| Secure configuration | Kyverno PSS, `baselines/` (F10), kube-bench |
| Acceptable use / people | organisational, template only |

**Rules for every template:**
- Open with: "TEMPLATE for a notional organisation, not an adopted policy. Bracketed items are decisions your
  organisation must make."
- Each policy statement that the lab enforces carries an inline `→ enforced by` link to the file *and* an
  `→ evidenced by` link to a sample, where one exists. That pairing is the core lesson: a policy that names its enforcing
  control and its evidence is auditable.
- Each template has a metadata block: owner role, approval body, review cycle, version and related controls (ISO/DORA/NIST).
- Don't copy policy text from any copyrighted source. Write it fresh.

**Tests:** every `→ enforced by` and `→ evidenced by` link resolves, and every template has the banner and the metadata block.

**Done when:** tests pass, and the SoA CSV (T15) links each organisational control to its template.
