## What it is, in plain English

**apko** builds container images from a short YAML list of packages, producing the same image from the same input. **Wolfi** is a security-focused Linux distribution built for containers, with very few packages and a fast patch cadence. An **SBOM** (software bill of materials) is a machine-readable ingredients list, here in **CycloneDX** format generated by **syft**.

## Why it is here

Fewer packages mean fewer vulnerabilities and less to trust. An SBOM lets you answer 'are we affected?' when a new vulnerability is announced.

## How this repository uses it

- `apko.yaml` lists `wolfi-baselayout`, `ca-certificates-bundle`, `python-3.13` and `busybox` only.
- CI smoke-tests the built image (a real `import sqlite3`), checks `/bin/sh` exists, then signs and attests.
- `images/generate-roi.py` builds a Register of Information from the repo's chart and image inventory.

## If it fails

The canary image cannot be rebuilt. The deployed image keeps running.

## What we learned the hard way

Real problems found by running this component, not by reading about it (from the [CHANGELOG](https://github.com/Utility-SOC/dora-blueprint/blob/main/CHANGELOG.md)):

- apko's Go module path is `chainguard.dev/apko`, not the GitHub URL.
- GHCR repository names must be lowercase, but the org name is mixed-case.
- `crane digest` right after a push hit propagation lag. The digest is now parsed from apko's own output.
- The register generator found **zero** Helm components after the tier split (it only looked in `apps/*.yaml`). Found and fixed by the tests.

## Limits and honest caveats

- **The build tool itself is unpinned** (`apko@latest`), which is a supply-chain weakness in a supply-chain feature. Pin it.
- The register's contract, jurisdiction and exit-strategy fields are **synthetic** and marked so.
