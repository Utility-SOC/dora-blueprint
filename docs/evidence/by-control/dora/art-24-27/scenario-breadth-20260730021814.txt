=== four real bugs found running these live, not assumed from a clean apply ===

1. node-kill's own recovery step ("kubectl taint ... unreachable:NoExecute-") returned
   `error: taint "node.kubernetes.io/unreachable:NoExecute" not found` during a real run -- the
   taint had already been reconciled away by the time recovery ran (a real, live-observed
   Kubernetes behavior, not a script bug -- the `|| true` guard already in place handled it
   gracefully and the drill still completed correctly).

2. pvc-corruption-restore's own detection step aborted the whole workflow on its first real run:
   `verify.py --field` intentionally exits 1 whenever integrity_check is "fail" (so callers like
   ns-restore can treat a post-restore failure as a real error), but this scenario deliberately
   corrupts data first and *expects* fail at that point -- and the container runs under
   `bash -ceu`, so capturing that expected non-zero exit aborted the script before recovery ever
   ran. Fixed with `|| true` on all four verify.py calls that can legitimately see
   integrity_check=fail. Commit d3c46e2.

3. The same drill's recovery step then hit a real RBAC Forbidden error deleting the Deployment:
   the ClusterRole granted `pods` delete but never granted `persistentvolumeclaims` or
   `deployments` (apps) delete at all. Commit 5ef3627.

4. network-partition's own probe function double-counted curl's "no response" placeholder: curl's
   own `-w '%{http_code}'` already prints "000" on connection failure, but the function's
   `|| echo "000"` fallback fired too (curl still exits non-zero after printing its own "000"),
   producing "000000" -- which never matched the `"000"` comparison, so a real, working deny was
   reported as verdict=fail. Commit fb00683.

A fifth issue (not a workflow bug) surfaced building the trend dashboard: a bare
`{...} | json ... | unwrap rto` is invalid LogQL -- unwrapped values are only valid inside a
range-vector aggregation (`max_over_time(<selector> | unwrap <field> [<range>]) by (<label>)`).
Fixed and verified directly against the live Loki instance. Commit d4070e2.

=== node-kill (drill_id node-kill-20260730020314) ===

t_inject=2026-07-30T02:03:24Z -- tainted resilience-lab-worker-1 (the node canary-writer was
actually running on) with node.kubernetes.io/unreachable:NoExecute, then force-deleted the pod.

Real finding, different from what the plan speculated in advance: a replacement pod reached
Running on the *same* node within the 60s observation window, while the node was still tainted.
This is real, correct Kubernetes behavior, not a drill bug: pods get a default 300s
tolerationSeconds against exactly this taint (the DefaultTolerationSeconds admission plugin), so
a freshly-scheduled pod tolerates the "unreachable" taint for up to 5 minutes -- combined with
canary's PV being node-local (openebs-hostpath), the replacement pod had nowhere else it *could*
schedule anyway. The taint alone, without also removing the pod's default toleration, does not
by itself prevent a new pod from landing right back on the tainted node. Recorded honestly as
observed, not as the more dramatic "stuck Pending" outcome originally guessed at in the plan.
